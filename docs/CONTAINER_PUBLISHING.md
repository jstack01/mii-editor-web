# Manual GHCR publishing — approval required

No push/tag/release happens during D3 preparation. The workflow is workflow_dispatch only: no push, pull-request, schedule or automatic release trigger. `publish` defaults to false. All actions are pinned to commits. Verification has contents:read only; only the conditional publishing job requests contents:read and packages:write, authenticating with the repository's short-lived GITHUB_TOKEN. No PAT, Docker Hub account, password or extra secret is required by this workflow.

Read-only API inspection confirmed Actions is enabled, official actions are allowed, and the default workflow token is read-only. An explicit job-level packages:write request is therefore supplied. The current GitHub CLI already has repo/workflow scopes for the eventual approved workflow-file push. Actual GITHUB_TOKEN package-writing permission cannot be proven locally before the approved workflow runs. Disabled Issues/PRs/Discussions/Wiki are unrelated and must remain unchanged.

## After the owner approves the first public upload

1. Review the clean source commit, Docker/Compose configuration, test reports, licenses/asset-rights disclosures and version. Build/test all ZIPs and the image from the same clean commit. Confirm no original/private files are tracked or sent in the build context. Do not overwrite existing Git or image version tags.
2. Explicitly push the approved source to the existing repository/main. This installs the manual workflow but does not publish a container. Do not create another repository or push to Docker Hub.
3. Run a verification-only workflow if desired: `gh workflow run container.yaml --ref main -f version=v0.1.0-preview.4 -F publish=false`. Inspect `gh run list --workflow container.yaml`, then `gh run watch RUN_ID --exit-status`. These workflow runs build/execute AMD64 and emulated ARM64 on the Ubuntu runner; they are not native ARM hardware certification.
4. After explicit image-publication approval, dispatch the same workflow with `-F publish=true`. The source revision is the dispatched commit. Verification runs first; publishing checks version/package access, refuses existing version tags and publishes a single linux/amd64+linux/arm64 index to ghcr.io/jstack01/mii-editor-web:v0.1.0-preview.4. OCI source/revision labels associate it with the existing repository. No floating latest tag is created.
5. **First-package visibility is a separate gate.** GHCR packages can be private despite a public source repo. Repository association inherits access, not visibility. GitHub documents changing package visibility in the package Settings UI; the documented REST packages API does not provide a visibility-update endpoint. Do not invent an API call or claim automatic public status. If authenticated UI tools are available, Codex can perform the approved setting; otherwise the minimum owner action is opening the package settings and selecting Public once. Open https://github.com/jstack01?tab=packages, select the new package and Package settings; follow GitHub's access/visibility documentation. Never request a password/token.
6. The workflow's final anonymous verification intentionally fails if the image is private. After changing visibility, do **not** rerun the publishing job for the same tag (the overwrite guard will reject it). Instead run: `python3 scripts/verify-ghcr-anonymous.py --version v0.1.0-preview.4 --digest PUBLISHED_INDEX_DIGEST --expected-commit FULL_COMMIT --pull --output release/container-publication-v0.1.0-preview.4.json`. This uses an anonymous registry token and a fresh empty Docker credential config, preserving the owner's normal credentials. It verifies both manifest platforms, unauthenticated package-public/repository metadata and actual unauthenticated pulls, plus source/revision labels. Do not print account/registry tokens. Anonymous verification is the completion gate, not merely a successful authenticated upload.
7. Only after that report passes, use the existing guarded scripts/publish-release.py with the approved version/commit and explicit upload flag to create the GitHub version tag/prerelease and attach the four ordinary ZIPs, Docker starter ZIP and combined checksum file. The helper requires the matching anonymous-publication report for Docker releases. It must not label a private/unpullable container as ready. Previous preview.1/2/3 tags, releases and assets remain unchanged.
8. Download the published release assets, verify checksums/source-snapshot exclusions, read back repository settings and package repository/public visibility, and perform one more empty-credential pull. Provide the release, GHCR and download URLs to the owner. No future commit publishes automatically.

## Local validation without publication

`docker buildx build --platform linux/arm64 --load -t mii-editor-web:test --build-arg VERSION=v0.1.0-preview.4 --build-arg REVISION=FULL_COMMIT --build-arg SOURCE_DATE_EPOCH=COMMIT_UNIX_TIME --build-arg BUILD_DATE=COMMIT_RFC3339_TIME .`

On a capable builder, export `--platform linux/amd64,linux/arm64 --output type=oci,dest=/tmp/mii-editor.oci.tar --metadata-file /tmp/mii-editor-build.json`; inspect the index and both layers/configs without a registry push. Run scripts/verify-container.py for actual execution/HTTP/filesystem/security checks. Run `node web/scripts/container-browser.mjs --url http://127.0.0.1:PORT/ --container TEST_CONTAINER --name docker-test` against a running test image for all 13 screens/presets/random/edit/file/XML/image/repair/share and persistence across docker restart. Never point its restart operation at an unrelated container.

To test the actual Compose file before the public image exists, assign the local build the intended GHCR tag using `docker tag` (local only), set an isolated host port, and run `docker compose -p mii-editor-d3-test up -d --pull never`. This is not an anonymous registry pull or public upload. Stop/down that project after testing. Scripts/configuration must be checked from a clean Git source snapshot without private original directories. No runtime application code change is needed.
